# GNOME Shell crash during the first inventory batch (2026-10-29)

Record of the crash that ended the first live batch of X11-FLASH-02. Tags: MEASURED (read from the
journal or from a file named here), INFERRED (follows from measured facts, not seen directly),
HYPOTHESIS (a possible cause nobody tested). Times are local (+05:30). The user name is replaced
by `USER`. The crash dump in `/var/crash` was not opened, copied or read; only `ls` metadata was
looked at.

## What was running

MEASURED. `xflash run --probe --apps xterm,gnome-text-editor,eog,google-chrome,firefox` started at
12:32:13 (`meta.json`), 14 planned runs, shuffled with seed 7. Three runs had started when the Shell
died (`runs.jsonl`):

| 2 | gnome-text-editor, X11 | 3462464370 | 0x1200004 | 12:32:31.7 | closing when the Shell died |

MEASURED. 0x1200004 is run 2: the observer file has `CreateNotify` for X window 18874372
(0x1200004) followed by `props` with `class=gnome-text-editor` and `pid=2686523`, and the run record

MEASURED. Both Chrome windows were `REJECT_UNMATCHED` by the extension: the arm was for
`Google-chrome` and the window class is `xflash-chrome` (set by `--class`). They were never
cloaked or placed. This is a runner defect (wrong class in the app table), not a cause of the crash.

## Findings

1. **Trigger.** MEASURED: the Shell aborted 6 ms after the extension logged the close of window
   3462464370 (`EXTERNAL_CLOSE`), which was the close the driver sent after its 2.5 s settle
   (12:32:31.99 + 2.5 s). The window had been spawned and focused by `spawn-at spawn` and was the
   focus window. INFERRED: the abort is Mutter 46.2 unmanaging the focused XWayland window
   after failing to hand focus to another window (`Failed to focus window W1043 while avoiding
   0x1200004`), then asserting `focus_window != window`. The earlier xterm windows of this session
   were closed the same way (spawn-at close by id) without a crash (MEASURED, the 12:24 to 12:27
   tests), so closing a focused window is not enough by itself.

2. **Who sent `_NET_ACTIVE_WINDOW` with timestamp 0.** Unknown. What is measured: the message
   arrived 4 ms after the X window was created (observer: `CreateNotify` at 811186.0185 s monotonic;
   journal 12:32:31.954) and before the extension's own `WINDOW_CREATED` (31.990). Checked in the
   order asked:
   - Extension. MEASURED: the run-2 batch has no `RAISE` or `ACTIVATE` line (they are logged by
     `_focusWindowObject`, `assets/gnome/modern/extension.js:1470-1479`). Its focus calls are
     `window.activate(...)` inside the Shell, which is not an X client message. The only focus
     paths in a batch are `extension.js:999` and `:1006`, both conditional on a minimised or
     covered window or deferred focus; neither line was logged.
   - Our tools. MEASURED (grep): `tools/src/run.rs` has no X11 code at all; `tools/src/obs.rs`
     imports no `send_event`, `ClientMessage`, `configure_window`, `map_window` or focus request. Its
     only writes to the server are `ChangeWindowAttributes` (own event mask), `DamageCreate`,
     `DamageSubtract`. So neither tool can send `_NET_ACTIVE_WINDOW`. The `spawn-at` CLI has such a
     call only in the X11 driver (`src/platform/linux/x11/session.rs:664`), which the CLI does not
     use under GNOME (INFERRED from `ARM_SPAWN` in the extension log, i.e. the GNOME backend ran).
   - The application. INFERRED, not proven: gnome-text-editor (GTK4, `GDK_BACKEND=x11`) was the
     only other X client that touched 0x1200004. HYPOTHESIS: GTK's X11 `present` path sends the
     message with time 0 when the window is mapped without a user timestamp.

3. **Did the driver close or kill the focused window?** MEASURED: it closed it, gracefully, with
   `spawn-at close --id 3462464370` (a request through the extension; the extension logs
   `EXTERNAL_CLOSE`). The run record for run 2 has no `killed` entry because the run never finished.
   MEASURED (read from source): `run.rs` calls `signal()` only for the observer pid, the CPU burner pid, a timed-out
   `spawn-at spawn` child, and the window pid of an app marked `kill_ok` after a failed graceful close
   (`run.rs:523, :561, :568, :647, :652`). None was reached in run 2.

4. **Exit 137.** INFERRED: the command was killed when the session ended, not by the tool. The
   batch ran for about 37 s of a 400 s `timeout`, so `timeout` did not fire. The Shell died at 12:32:34;
   the unit exit was logged at 12:32:50 and Claude Desktop (which hosts the Claude Code session)
   logged `Broken pipe` at the same second. The shell that ran the command, `timeout` and `xflash` were
   under that desktop scope. No OOM line was found in the journal for 12:32:00 to 12:34:30
   (MEASURED, grep). Who sent the SIGKILL (systemd scope teardown or the desktop app itself): cannot
   tell.

5. **Observer buffering.** MEASURED: the output of this batch was 1130 lines, 121 KB in 36.7 s
   (108 `DamageNotify`). `obs.rs` writes each line through a `LineWriter` and keeps only the window
   table and an atom-name cache, so it does not buffer events. INFERRED risks: (a) every
   `PropertyNotify` of a watched property triggers about 9 synchronous property reads (`props()`), so a
   title or hint storm makes the observer slow and lets the server queue events for it; (b) raw damage
   rectangles from a browser could reach hundreds of lines per second. Estimate, INFERRED:
   idle apps about 0.2 MB per minute, a busy browser 5 to 10 MB per minute. No memory growth was
   measured; the Shell's own peak was 7.1 GB over its 19 h of life (journal, `Consumed ... 7.1G memory
   peak`), which says nothing about this batch.

6. **Earlier damage to the Shell.** MEASURED: before any live action of this work (first test
   about 12:24, baseline tests 12:22 to 12:23) the Shell had logged at 12:11:18 `Invalid window geometry
   for xdg_surface@57`, three `meta_window_set_stack_position_no_sync: assertion 'window->stack_position
   >= 0' failed`, at 12:11:20 `value "inf" ... property 'scale-x'` and `Error in size change accounting`
   (also 12:11:24 and 12:11:35). HYPOTHESIS: a Wayland window left in a broken state (`W1043`?) was
   still in Mutter's focus list at 12:32 and could not take focus, which is what the `Failed to
   focus window W1043` line says. Not tested.

## What was changed because of this

See the commit that follows this file: the run driver now writes a progress file after every run and
resumes from it, runs one application at a time with a wait for the window to be gone, closes
gracefully, records the Shell pid and boot id and stops on a change, runs under a memory-limited
scope, and the observer is rate-limited and no longer reads properties on every property event.
The Chrome entry used the wrong class (`xflash-chrome`, not `Google-chrome`).
