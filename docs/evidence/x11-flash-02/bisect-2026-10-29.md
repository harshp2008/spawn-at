# Bisect in a private headless Shell: no crash reproduced (X11-FLASH-02f)

Tags: MEASURED (a run or a read in this work, raw data under `data/bisect/`), INFERRED, HYPOTHESIS.
Everything here ran in a private headless GNOME Shell (own bus, own Wayland socket, own Xwayland,
own keyfile gsettings, a copy of the extension). Nothing was launched on the maintainer's live
session. The live Shell was pid 2718897, start time 81373971, before and after (MEASURED).

## 1. The private Shell

MEASURED. Started by `tools/psh-start.sh`, used only through `tools/psh` (refuses unless the private
socket, display, bus and Shell pid are the private ones and none is the live one), stopped by
`tools/psh-stop.sh` (signals only recorded pids and processes carrying the sandbox tag
`PSH_SB=<sandbox>`; removes the sandbox after `findmnt -M`). Each bisect cell got a fresh Shell.

| What | Result |
| :-- | :-- |
| Extension loaded | `ProtocolVersion` 7 over the private bus; copy of `assets/gnome/modern/` is `diff -r` identical to the installed extension |
| Private vs live | private monitor list: one 1920x1080 monitor with a 1920x1048 work area; live: 1920x1040 |
| Windows | only in the private Shell (`spawn-at query windows` on the live bus listed only the live windows throughout) |
| Observer | `hello` record `display: ":2"`, the private Xwayland |
| Smoke test | xterm, 3 runs, all `ok`, `data/smoke/` |
| Crash detection | killed ONLY the recorded private Shell pid: `psh` refused (exit 98) and the batch tool stopped; `psh-stop` removed the sandbox; `psh-start` made a new Shell |

Deviations from the design in `isolation-feasibility.md`, each found by trial:
1. `systemd-run` must be given the live bus (it only creates a memory-limited scope); the Shell
   sources the private environment inside the scope.
2. The public X display is not the newest socket. Mutter logs "Using public X11 display :2, (using
   :3 for managed services)"; a client on :3 hangs. `psh-start` reads the log line.
3. The Shell opens its X11 display only after asking systemd to start
   `gnome-session-x11-services.target`. The private bus has no systemd, so the first attempt ended
   with "Failed to initialize X11 display" and every X client hung. Fix: `tools/src/bin/sysd1stub.rs`,
   a stand-in for `org.freedesktop.systemd1` on the private bus (answers `Subscribe`, `StartUnit` with
   a job and `JobRemoved`; starts nothing).
4. Mutter's Xwayland authority file lives in the private runtime directory; `XAUTHORITY` is set to it.
5. A headless Shell starts helpers (ibus, gvfs, evolution, at-spi); `psh-stop` ends them by sandbox tag.
6. The Shell's stderr prefixes the extension's lines (`(gnome-shell:PID): ... **: time: [spawn-at-time]`);
   `xflash` finds the tag inside the line.

What can still leak (INFERRED): `/tmp/.X11-unix` socket numbers, one transient scope in the live
user manager per Shell, an apport crash file if the private Shell crashes (none was written), CPU and
memory. No write to the live dconf, `~/.config`, `~/.cache`, `~/.local` or enabled-extensions was
made by the private session (its environment points all of them into the sandbox).

## 3. What this shows and does not show

- MEASURED: with the same app, the same spawn-at path, a focused window and the same graceful close,
  the Shell did not crash and never logged the timestamp-0 warning. Not once in 69 runs, including 27
  of the exact crashing configuration (cells 5, 7, 8, 10 with focus, and cell 11).
- MEASURED: xterm runs under the live session (80) were also closed with the window focused
  (`focused_at_close: true` in all 80 records). So "closing a focused XWayland window" is not enough
  to crash the Shell, in the live session or the private one. The earlier verdict on H6 is weakened.
- INFERRED: the crash needs something the private Shell does not have. The private Shell differs from
  the live one in: no gnome-session, no portals, no gsd daemons (xsettings, input), no GDM, no real
  input device and so no user-activity time, a fresh Shell with no history, a systemd stub, a single
  virtual monitor, and no other applications. The live Shell was 9 days old and showed degraded
  warnings (invalid geometry, size accounting, stack_position, `inf` scale) before any batch.
- HYPOTHESIS, not tested: the timestamp-0 message comes from GTK sending `_NET_ACTIVE_WINDOW` when
  the app gets a user-activity time from the live session's input; the private Shell has none.
  The startup-id arithmetic (see `startup-id-lead.md`) is a real specification mismatch but has no
  demonstrated effect here.

## 5. Step 4: product bug

Not confirmed, so no bug report and no patch were written. The `_TIME` value is outside what the
specification describes (MEASURED arithmetic in `startup-id-lead.md`), which is worth fixing on its
own, but no run shows it causing a crash or the warning.
